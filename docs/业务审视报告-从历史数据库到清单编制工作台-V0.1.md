# 业务审视报告：从历史数据库到清单编制工作台

**审视日期：** 2026-08-02  
**审视范围：** 当前产品需求、数据模型、导入/关联/匹配逻辑、工作台与清单匹配界面；未修改代码。  
**适用场景：** 西安为主的单人工程造价师，本地管理历史项目，后续增加“清单编制”。

## 一、结论摘要

当前系统的定位和实现，**基本符合“个人历史造价数据资产库 / 参考价检索工具”**，不宜直接定义为“清单编制系统”。

它已建立了三个很有价值的基础：原始 Excel 可追溯、导入后复核发布、历史清单可检索和候选匹配。这三点是造价数据积累的正确起点。

但若后期将“造价数据工作台”调整为“清单编制”，现有的“清单、材料、定额分库并列检索”的实现方式不足以支撑真实业务。真实编制的中心不是三套库，而是**某一项目、某一专业、某一计价版本下的一份清单及其完整组价过程**。清单项需要绑定项目特征、工程量、计量规则、定额/人材机消耗量、价期与取费，且全过程可改、可算、可校核、可冻结、可导出。

建议保留现有历史数据能力作为“证据库和参考库”，但将后续系统重构为：

> **主数据（清单/定额/资源） + 历史案例与价格事实 + 项目清单编制工作台 + 规则/价期/版本控制。**

不要把历史项目中的一条清单或材料记录直接当作永久“库条目”，也不要让新项目通过“确认一个候选项”就完成编制。

## 二、当前实现与真实业务的符合度

| 业务能力 | 当前状态 | 业务判断 |
| --- | --- | --- |
| 原始资料留存与追溯 | 原文件按哈希归档；记录可到工作表、行和字段单元格 | 符合，且是后续可审计的核心资产。 |
| 历史项目版本 | 项目版本、草稿/发布、重复文件识别已具备 | 基本符合历史库；缺少“编制过程版本 / 计价版本 / 定稿锁定”语义。 |
| 历史清单检索 | 可按名称、编码、规格、地区、单位等检索 | 符合参考查询；不是编制界面。 |
| 清单—综合单价分析—定额关联 | 以清单编码做一对一关联；重复编码即不关联 | 仅适合非常规整的样例。真实报表中同编码多条、子目拆分、特征差异均常见，不能作为主关联策略。 |
| 材料/人工/机械 | 从“工料机”表独立入库；类别主要依据名称文字判断 | 不足。资源类别、规格、品牌、产地、税率、运输、损耗和价期没有被完整建模。 |
| 定额 | `QuotaItem` 只保存名称、编码、单位、消耗量，并附属于历史清单项 | 不足以成为定额库；缺定额册/章/节/子目、基价构成、换算、适用条件、版本和人材机消耗量明细。 |
| 综合单价组成 | `RateComponent` 仅有类别、名称、金额 | 可用于历史展示，不能用于重新组价或复算；缺数量、单位、单价、系数、计算基数和计算公式。 |
| 新清单匹配 | 输入名称和单位，输出历史候选与文本相似度评分 | 可做“找历史案例”；不能判定可套用、不能形成编制成果。 |
| 项目质量控制 | 有缺字段、金额不平、关联失败等检查 | 起点正确；尚未覆盖清单编制阶段的量价费税、取费顺序、漏项、重复项及口径校核。 |

## 三、最关键的业务错位

### 1. “三库”在当前数据模型中其实不是三个主数据仓

当前 `CostItem`、`ResourceItem`、`QuotaItem` 都首先是**某历史项目版本中的事实记录**。其中清单虽有 `library_bill` 标记，仍然依赖 `project_version_id`；材料和定额没有独立的标准库实体、来源层级或发布机制。

因此，当前更准确的名称是“从历史项目中抽取出的三类数据”，不是可被安全复用的清单库、材料库和定额库。若把它们直接作为编制基础，会把不同地区、时期、计价模式、成果阶段、税费口径混入同一选择面。

### 2. 当前工作台是横向检索台，不是以项目为中心的编制台

现界面把清单、定额、工料机、措施费、费率和指标放在一个统一筛选表中。这很适合回答“历史上有没有类似项、当时是多少钱、来源在哪”；但编制时用户需要持续面对的是：

1. 当前项目的清单树和分部分项层级；
2. 当前选中清单项的特征、工程量、单位与计算规则；
3. 该项的定额子目、资源消耗、市场价、取费和综合单价形成过程；
4. 当前项目的措施项目、规费、税金、专业汇总及总造价；
5. 修改某项后对全项目及版本差异的影响。

两者的心智模型完全不同。把检索工作台改名为“清单编制”会造成预期错配。

### 3. “匹配成功”不等于“可套用、更不等于可交付”

当前候选分主要来自编码、名称、描述、规格和单位；界面只要求用户输入名称、单位。真实可套用至少还要判断：专业、清单计量规则、项目特征/做法、结构部位、施工条件、是否含主材/设备、计价模式、地区、价期、成果阶段、税率及风险口径。

尤其是“确认并记住”当前会生成名称同义词规则。这会把一次项目层面的选择上升为全局语义规则，存在把“相似”误沉淀成“同类、可替代”的风险。应区分：同义名称、标准分类、可复用做法、项目内选用、历史参考价，且分别审批和适用。

### 4. 现有关联关系不能表达组价链

真实链条至少是：

```text
项目计价版本
  └─ 专业 / 单位工程 / 分部 / 分项清单项
       ├─ 项目特征、计量单位、工程量、清单计量规则
       ├─ 组价方案（可有多个方案）
       │    ├─ 定额子目及换算系数
       │    ├─ 人工、材料、机械消耗量
       │    ├─ 资源价格（价格来源、价期、含税口径）
       │    └─ 管理费、利润、风险等取费规则
       └─ 综合单价、合价、引用历史证据、人工调整及理由
```

当前模型中的“清单项—金额型组成项/定额项”只能保存一段历史结果，不能表达、计算和回溯这条链。

## 四、从造价工程师视角的主要风险（按优先级）

### P0：进入清单编制前必须解决

1. **缺少项目编制域。** 没有单位工程、专业、章节树、当前清单行、编制状态、计算结果、成果版本和锁定机制；无法形成一份连续可交付的清单成果。
2. **缺少可复算的组价模型。** 金额型 `RateComponent` 不能说明“某材料消耗多少、单价何来、损耗/系数如何取、哪一项费用以什么为基数计算”。
3. **缺少价期和价格口径模型。** “价格”当前只有单价/金额，未区分除税/含税、信息价/询价/结算价、供应商、税率、运杂费、采保费、品牌产地、有效期和适用地区。跨项目引用风险高。
4. **定额库不是定额库。** 需将定额主数据与项目套用记录分离；否则无法管理定额版本、补充定额、换算说明、适用范围、组成消耗量和停用状态。

### P1：投入真实项目试用前应解决

5. **关联键过于单薄。** 仅按清单编码关联会在同编码不同特征、分部重复、清单行拆分或分析表按行号/父级组织时失效。应保留原始层级路径、行号、父行、唯一业务键和关联置信度，并支持人工确认。
6. **资源类别识别不可靠。** 依据名称中是否包含“人工/机械”判断，容易把材料、台班、设备、主材、甲供材识别错误。应读取报表分类列并允许映射、复核。
7. **单位换算缺少适用条件。** 一个全局换算系数无法处理包装规格、密度、厚度、损耗、材质、地区规范等条件；转换必须具有条件、来源、有效范围和禁止自动换算的策略。
8. **项目画像不足以保证可比。** 当前“结构形式、面积口径、地上/地下面积”齐全即进入标杆池过于宽松。至少还需工程类别、档次、层数/高度、结构/基础、地下室、合同与计价模式、材料档次、成果阶段和价格基准口径。

### P2：规模化使用前应解决

9. **查询性能与可治理性。** 工作台逐项目遍历并拼接多类记录，随着数百项目和大量资源记录增长，检索、统计和质量检查会变慢；需要面向检索的索引/物化视图及统一事实视图。
10. **“发布”粒度偏粗。** 历史项目发布适合资料入库；清单编制还需要草稿、校核、送审、定稿、回退、复制估算方案、差异对比和冻结引用价。
11. **成果导入/导出闭环不足。** 后续必须明确输出目标（广联达接口/Excel 标准模板/计价成果表）及字段映射，否则只能产出内部参考表，无法进入常规交付流程。

## 五、建议的目标架构与边界

### 5.1 四层数据结构

| 层级 | 应保存什么 | 核心原则 |
| --- | --- | --- |
| 原始证据层 | 原始 Excel、工作表、单元格、导入批次、解析结果 | 不改写，可追溯。保留当前能力。 |
| 主数据层 | 标准清单项、清单特征模板、定额册/子目/消耗量、标准资源、单位/分类/取费规则 | 有来源、版本、适用范围、状态；不是某项目的价格事实。 |
| 事实与案例层 | 历史项目清单、已发生资源价格、历史组价、指标 | 必须带项目、地区、价期、计价模式、成果阶段、税费/价格口径和可信状态。 |
| 编制工作层 | 新项目计价版本、清单树、工程量、组价方案、调价记录、措施/取费、校核、成果版本 | 可以编辑、试算和冻结；引用主数据与案例，但不污染它们。 |

### 5.2 三库应如何定义

- **清单库：** 标准编码、名称、单位、计量规则、专业/章节、项目特征字段模板、典型做法和适用范围。历史项目清单是“案例”，不是默认标准条目。
- **定额库：** 定额版本—章节—子目—人材机消耗量—基价/换算规则的完整层级。项目内实际套用应是独立的“定额应用记录”。
- **材料库：** 标准资源（材料/设备/人工/机械/台班）与“价格序列”分离。价格记录必须标明规格、品牌、税口径、价期、地区、来源、有效性和是否可用于编制。

### 5.3 后期“清单编制工作台”的推荐布局

左侧为单位工程/专业/分部清单树，中部是当前清单行表格，右侧为选中项的“项目特征—工程量—组价—历史证据—校核”面板；底部或独立页处理措施、取费、汇总和版本差异。检索库应保留为右侧引用面板或独立“案例检索”，而非取代编制主界面。

## 六、建议的真实业务流程

1. **立项与计价环境锁定：** 建立项目、单位工程、专业、地区、计价依据/定额版本、价期、税率、成果阶段和面积口径。
2. **导入或编制清单：** 保留完整清单层级、编码、名称、特征、单位、工程量、暂估/甲供标识和来源；支持人工新增、拆分、合并与调序。
3. **标准项与历史案例辅助：** 推荐清单特征模板、可引用定额和历史案例；显示“可用原因”和“不适用原因”，由用户选择引用方式。
4. **逐项组价：** 套定额/补充子目、录入换算系数、形成资源消耗，选择价格来源与取费规则，系统实时计算综合单价与合价。
5. **措施与总价形成：** 在项目维度处理措施费、规费、税金、专业汇总和总造价，避免将它们当作与清单行完全平级的检索记录。
6. **校核与复核：** 检查工程量、量价乘积、消耗量、漏项/重项、取费基础、价期、异常单价、未定价项、低置信度引用和项目指标。
7. **版本冻结与导出：** 定稿时冻结所引用的定额版本、价格记录和规则快照；导出成果，同时保留差异和调整理由。

## 七、分阶段落地建议

### 阶段 A：先把历史库做“可信”（建议优先）

- 用 5–10 个真实脱敏广联达项目建立金样本：覆盖土建/安装、单层/多层表头、同编码多特征、综合单价分析、定额、工料机、措施和取费表。
- 定义每类表的字段覆盖率、关联准确率、金额校核通过率、人工复核时长和错误类型；达到阈值再批量导入。
- 将“历史案例”“标准主数据”“原始事实”在界面和数据层显式分开。
- 先把匹配改为“候选案例 + 可比性说明 + 引用方式”，不要承诺自动套用。

### 阶段 B：建设编制最小闭环

- 新增“项目计价版本—单位工程—专业—清单树—清单项—组价方案”模型。
- 仅选择一个专业（建议土建）和一个明确的计价体系/定额版本，完成“导入清单 → 逐项组价 → 措施/取费 → 校核 → 参考表导出”。
- 第一个版本可允许定额和价格人工选择，不追求 AI 自动组价；关键是全过程可复算、可回退、可追溯。

### 阶段 C：再扩展主数据和智能化

- 独立维护定额、资源和价格序列；引入价格有效期、地域/品牌/税口径筛选。
- 将 AI 限定为：特征拆解、候选召回、差异解释、异常提示；所有正式套用和价格采用必须由用户确认。
- 增加成果模板、跨版本差异、口径锁定和长期规则治理。

## 八、近期产品决策建议

1. 保持当前产品名称/定位为“历史造价数据资产库”；不要提前把主入口命名成“清单编制”。
2. 将现有“造价数据工作台”更准确地命名为“数据检索与证据工作台”或“历史案例工作台”。
3. 在开始编制功能前，先形成一份《清单编制业务规则与成果口径说明》：明确地域、专业、定额版本、税费规则、导入来源、输出格式和用户确认点。
4. 以真实脱敏样本开展业务验收；当前自动化测试通过只能证明样例工作流可运行，不能证明对真实广联达资料和可交付编制成果适用。

## 九、本次审视依据与限制

已审阅产品需求、数据字典、SQLAlchemy 数据模型、Excel 解析与关联逻辑、检索/匹配/指标计算逻辑、前端工作台与匹配界面，并运行现有测试：后端 8 项、前端 1 项均通过。

本次没有接触真实脱敏项目文件、地区计价依据或目标交付模板，因此对“某类广联达导出是否可完全解析”“某定额版本和取费规则是否正确”的判断不作验收结论。这些应在阶段 A 用金样本和造价师逐表复核完成。
