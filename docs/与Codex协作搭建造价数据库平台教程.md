# 与 Codex 协作搭建个人造价数据库管理平台

> 从对话、需求澄清、技术选型、界面设计到工程交付的实战教程  
> 案例项目：个人造价数据库管理平台（衡鉴造价库）  
> 整理日期：2026-07-25

## 1. 这份教程解决什么问题

这不是一份现成软件的操作说明，而是一份“如何与 Codex 合作把一个想法搭成软件”的执行教程。读者不需要先会写代码，但需要愿意承担产品负责人和领域专家的角色：说明真实问题、提供样本、确认专业口径，并验收 Codex 的阶段性产物。

这份教程以个人造价数据库管理平台为案例，回答五个问题：

- 开始时应该向 Codex 说什么，避免只得到一份泛泛方案？
- 一个复杂项目应该拆成哪些阶段，每一阶段结束时留下什么文件？
- 如何让 Codex 先理解业务，再做架构、UI 和代码？
- 如何检查 Codex 的输出，避免“看起来完成，实际上不可用”？
- 如何把聊天中的结论沉淀为别人可继续执行的项目资产？

## 2. 先建立正确的协作关系

### 2.1 双方角色

用户是产品负责人和领域专家，负责：

- 说明真实工作场景、现有做法、痛点和优先级。
- 提供脱敏的 Excel 样本、输出模板和专业规则。
- 对“什么算正确、什么可以接受”作最终判断。
- 确认涉及数据外发、删除、恢复、发布等高风险操作。

Codex 是产品、设计和工程执行者，负责：

- 阅读项目文件和代码，主动建立上下文。
- 把模糊目标转化为需求、边界、方案和任务。
- 编写或修改代码、文档、测试和配置。
- 运行构建、测试和检查，并报告真实结果。
- 明确区分已完成、待验证、假设和风险。

### 2.2 最重要的原则

1. **文件是长期真源，聊天是协作过程。** 关键决定必须进入 PRD、架构文档、设计规范、README 或决策记录，不能只留在聊天里。
2. **一次对话聚焦一个可验收目标。** “把整个系统做完”很难验收；“用 5 个样本验证广联达清单表导入”可以验收。
3. **先证据后结论。** 要求 Codex 读取现有文件、运行检查、引用具体代码或样本，再给判断。
4. **先闭环后铺开。** 先完成一个从输入到输出可验证的纵向流程，再扩展更多页面、来源和 AI 能力。
5. **专业判断不外包。** Codex 可以提出候选和理由，造价口径、数据可信度和最终采用结果仍由人确认。

## 3. 一条高质量指令的五个部分

与 Codex 对话时，尽量同时给出以下五类信息：

| 部分 | 应说明的内容 | 本项目示例 |
| --- | --- | --- |
| 背景 | 谁在什么场景下遇到什么问题 | 单人工程造价师，本地积累约 380 个项目的 Excel |
| 目标 | 本轮结束时要得到什么 | 输出经过样本验证的数据字典和导入规则 |
| 约束 | 不能做什么、必须遵守什么 | 不修改原始 Excel；本地运行；AI 只发必要片段 |
| 交付物 | 文件、代码、页面或报告 | `docs/数据审计报告-V0.1.md` 和字段映射表 |
| 验收标准 | 如何判断完成 | 5 个样本均可追溯；未知字段全部进入异常报告 |

可直接复用的基础模板：

```text
项目背景：<用户、场景、已有资料和当前状态>。

本轮目标：<一个可以验收的结果>。

请先阅读：<文件路径或样本目录>。先总结你理解到的事实、缺口和假设；
如果现有资料足够，就直接执行，不要只给计划。

约束：
1. <业务边界>
2. <技术或数据安全边界>
3. <不要改动的内容>

交付物：<明确文件或功能>。

验收标准：
1. <可运行或可核查条件>
2. <错误、边界和回退条件>
3. <需要执行的测试或构建命令>

完成后请说明：改了什么、验证结果、仍有哪些风险或待确认项。
```

## 4. 项目从零到可交付的整体搭建路线

建议按下列顺序推进。每一阶段都要留下可追溯的文件，并在退出条件满足后再进入下一阶段。

| 阶段 | 核心问题 | 主要产物 | 退出条件 |
| --- | --- | --- | --- |
| 0. 目标定义 | 为什么做，第一版解决什么 | 项目简报、成功标准 | 目标和非目标可检查 |
| 1. 需求访谈 | 用户实际怎么工作 | PRD、待确认问题 | 核心流程和边界明确 |
| 2. 数据审计 | 真实 Excel 到底长什么样 | 样本清单、数据字典、模板差异 | 关键字段和关联可验证 |
| 3. 技术选型 | 如何在约束内实现 | 架构文档、决策记录 | 关键取舍有证据和门槛 |
| 4. 交互与视觉 | 用户如何高效完成任务 | UI 规范、关键页面原型 | 核心流程可走通 |
| 5. 工程基线 | 项目如何运行、测试、迁移 | 代码骨架、脚本、CI/检查 | 新环境能按文档启动 |
| 6. 纵向闭环 | 最小真实价值能否跑通 | 导入到追溯的完整功能 | 真实样本端到端通过 |
| 7. 扩展能力 | 检索、对比、匹配、AI | 分阶段功能与测试 | 每项能力独立降级可用 |
| 8. 交付运维 | 如何备份、恢复、升级 | 打包物、恢复演练、交接文档 | 可重复安装和恢复 |

> 本案例在沟通中先完成了需求和技术选型，随后生成 UI 方向和后端代码骨架。真实 Excel 样本审计仍是关键门槛。对类似项目，更稳妥的做法是把数据审计放在技术细化和大规模编码之前。

## 5. 阶段 0：把想法变成可检查的目标

### 本阶段要回答

- 谁会使用？多长时间使用一次？
- 最痛的三个问题是什么？
- 第一版完成后，用户能做成哪件以前做不到或很费时的事？
- 哪些能力明确不做？

### 推荐对话

```text
我想做一个个人造价数据库管理平台。我的历史数据主要是广联达、
斯维尔、宏业和自制 Excel，大约 380 个项目。我是单人使用，
希望在本地运行。

先不要写代码。请用产品访谈的方式帮我把目标澄清成：目标用户、
核心问题、第一版目标、非目标、成功标准、最大不确定性。
一次只问最影响方向的问题；已能从回答中推出的内容不要重复问。
最后把结论写入项目简报。
```

### 人工检查点

- 目标是否描述了用户结果，而不是堆功能名？
- 非目标是否足够明确，例如“不自动生成最终预算”“不覆盖原始 Excel”？
- 是否写出了最大不确定性？本案例最大的早期不确定性是真实 Excel 的结构差异。

## 6. 阶段 1：通过需求访谈形成 PRD

### 本阶段输入

- 当前工作流程和常见文件类型。
- 数据规模、地区、计价模式、专业和成果阶段。
- 查询、比较、匹配、指标计算等典型任务。
- 敏感数据、备份和 AI 外发边界。

### 推荐对话

```text
请基于刚才的访谈整理产品需求文档，先阅读项目简报。

PRD 至少包含：背景、目标、非目标、用户与环境、数据范围、项目元数据、
历史项目导入、查询、参考价匹配、综合单价对比、指标计算、原始数据保护、
版本与追溯、质量控制、AI 边界、安全备份、第一版范围、验收标准和待确认问题。

不要把未确认内容写成事实；使用“已确认 / 假设 / 待验证”标记。
请将文档保存到 docs，并在最后列出下一轮最应该补充的资料。
```

### 应得产物

- `docs/产品需求文档-V0.1.md`
- 明确的第一版必须项、后续项和非目标。
- 一组等待样本或专业人员确认的问题。

### 人工检查点

- 每个核心结果能否追溯到原始文件、工作表和位置？
- 原始值、系统计算值、规则匹配值、AI 建议是否严格区分？
- 价格可比性是否包含地区、时间、税率、单位和计价口径？
- AI 不可用时，核心工作是否仍能继续？

## 7. 阶段 2：用真实数据审计校正所有假设

这是本类项目最重要、也最容易被跳过的阶段。没有样本，任何字段模型和导入规则都只是推测。

### 样本准备建议

- 选择 5 至 10 个脱敏项目，覆盖不同年代、广联达版本和专业。
- 包含清单计价、综合单价分析、工料机、定额、措施费和取费表。
- 至少包含一个合并表头、隐藏行列、公式较多或文件较大的异常样本。
- 原件只读保存，另建脱敏副本供分析。

### 推荐对话

```text
请审计 samples/广联达脱敏样本 下的 Excel。不要修改任何原文件。

目标是建立第一版导入依据，不是直接做万能解析器。请输出：
1. 文件和工作表清单；
2. 报表类型、表头位置、字段及数据类型；
3. 合并单元格、隐藏行列、公式和缓存值情况；
4. 清单、综合单价分析、定额和工料机之间可用的关联键；
5. 模板差异、异常案例和无法确认项；
6. 第一版数据字典与来源坐标格式；
7. 可自动处理、必须人工复核和暂不支持的边界。

把结论写成 docs/数据审计报告-V0.1.md，并生成一份机器可读的字段映射配置草案。
所有结论请注明来自哪个样本和工作表。
```

### 退出条件

- 关键字段可定位，关联方式有样本证据。
- 数值精度、单位和公式缓存策略已确认。
- 未识别内容不会静默丢弃，而会进入异常报告。
- 已决定第一版支持哪些模板，不支持哪些模板。

## 8. 阶段 3：让技术选型服从业务约束

本案例的架构结论是：本地 Web 应用、Python 模块化单体、SQLite 单一事实源、React 前端、openpyxl 解析、FTS5 + RapidFuzz + 规则检索、云端模型适配层。它不是通用答案，而是由“单人、本地、约 380 个项目、低写并发、强追溯、暂不使用 Embedding”等约束推出来的。

### 推荐对话

```text
请先阅读 PRD 和数据审计报告，再做技术架构调研。不要为了显得先进而增加服务。

请比较候选方案并给出证据：业务主库、Excel 解析、全文检索、相似匹配、
后台任务、AI 接入、文件归档、备份恢复、前端框架和本地打包。

每个决定必须写明：采用什么、为什么、未采用什么、什么实测结果会触发重新评估。
重点验证数值精度、来源追溯、重复导入、版本发布、AI 降级和备份一致性。
输出 docs/技术架构调研与选型-V0.2.md。
```

### 人工检查点

- 是否先使用最简单、可维护的组件？
- 是否给复杂组件设置了“只有出现实测瓶颈才引入”的门槛？
- 数据库和原始文件各自保存什么，是否清楚？
- AI 是否被限制为建议层，而不是事实层？

## 9. 阶段 4：把专业工作流转成界面

### 先设计任务，不先设计页面

优先画出五条核心任务：

1. 导入历史项目并只处理异常。
2. 查询历史价格并定位原始证据。
3. 选择多个样本比较综合单价组成。
4. 为新清单逐项确认历史候选。
5. 备份、验证并在必要时恢复。

### 推荐对话

```text
请基于 PRD 和技术架构，为桌面优先的造价数据工作台设计 UI。
不要做营销首页，也不要把自然语言查询做成聊天气泡。

先输出信息架构和核心任务流，再制作“数据查询与来源追溯”这一张主屏，
并补充导入质量报告、清单匹配、综合单价对比、个人规则和备份设置。

要求：高密度表格、异常优先、证据就地可见；历史原始值、系统计算值、
规则匹配和 AI 建议必须用文字标签区分；适配 1280 至 1440 像素桌面宽度。
完成后提供实现约束和状态清单，不要只给静态漂亮图。
```

### 评审时让 Codex 自查

```text
请审查当前原型，不要直接改。按严重程度列出：
1. 是否存在无法完成的核心任务；
2. 是否缺少加载、空数据、部分失败、AI 离线、低可信度和只读状态；
3. 表格、抽屉和操作栏是否会在 1280px 下重叠；
4. 是否有把 AI 建议和历史事实混淆的表达；
5. 哪些设计难以用 React + TanStack Table 落地。
给出文件和具体位置后，再等我确认是否修改。
```

## 10. 阶段 5：建立可重复运行的工程基线

工程基线不是“文件夹已经创建”，而是另一台电脑可以按 README 完成安装、启动、迁移、测试和构建。

### 推荐对话

```text
请基于已确认架构建立工程基线。先检查当前仓库，不要覆盖已有改动。

需要交付：
- Python/FastAPI 后端与锁文件；
- SQLite + Alembic 初始迁移；
- React/TypeScript/Vite 前端；
- 本地开发启动脚本；
- 环境变量示例；
- 后端和前端最小测试；
- README 中的安装、启动、测试和构建命令。

验收：全新目录按 README 可启动；前端构建成功；后端测试成功；
健康检查可访问；所有写请求有本地会话保护；不提交密钥和运行数据。
请实际运行命令，不要只生成文件。
```

### 必须检查的基线清单

- 入口引用的文件都存在。
- `Makefile` 或脚本引用的路径都存在且可执行。
- 测试不是空目录；“没有收集到测试”不算测试通过。
- 前端 TypeScript 构建和后端导入均成功。
- 数据迁移能在空数据库创建，也能重复检查。
- README 的状态描述与代码现状一致。

## 11. 阶段 6：先做一个真实纵向闭环

最适合本项目的第一个闭环不是 AI 对话，而是：

```text
选择脱敏 Excel
→ 计算哈希并只读归档
→ 识别工作表和表头
→ 解析到暂存数据
→ 生成异常报告
→ 人工处理阻断项
→ 发布项目版本
→ 查询一条清单
→ 定位回原文件、工作表和行号
```

### 推荐对话

```text
请实现并验证“一个广联达样本从导入到来源追溯”的纵向闭环。
只支持数据审计已经确认的模板，不扩展未知格式。

采用测试驱动：先写会失败的解析、幂等、发布门槛和来源追溯测试，
再实现最小代码使其通过。使用脱敏黄金样本。

验收：
1. 原文件哈希归档且未修改；
2. 同一文件重复导入不产生第二份有效数据；
3. 无法解析的值进入异常报告；
4. 阻断错误未解决时不能发布；
5. 发布后能查询，并返回文件、工作表、行号；
6. 测试、迁移和前端构建全部通过。
```

## 12. 阶段 7：按价值扩展，不按技术炫技扩展

建议顺序：结构化查询 → 综合单价对比 → 规则匹配 → 新清单确认 → 指标计算 → AI 自然语言解析。每增加一项能力，都要保留没有 AI 时的基础路径。

### 对每项功能使用同一问法

```text
请实现 <功能名称>。先阅读 PRD 对应章节和现有代码。

先说明现有数据模型和 API 是否足够；若需变更迁移，解释兼容影响。
实现正常流程、空数据、错误、权限/安全、取消或回退状态。
补充与风险相称的测试，并实际运行相关测试和构建。

不要顺手重构无关模块。完成后按“行为变化、文件、验证、剩余风险”汇报。
```

## 13. 阶段 8：打包、备份、恢复和交接

对本地数据工具，备份只有经过恢复演练才算完成。

### 推荐对话

```text
请完成本地交付流程：前端生产构建、后端打包、首次启动初始化、
数据目录说明、备份、备份校验、暂存恢复、升级迁移和回滚说明。

请在临时数据目录做一次自动化恢复演练：创建数据和原始文件、备份、
破坏临时副本、恢复、校验记录数、SHA-256、项目版本和来源关系。
不得在测试中覆盖真实用户数据。

输出发布检查表和接手文档，并记录打包环境与版本。
```

## 14. 日常与 Codex 对话的实用模板

### 14.1 开启一个新任务

```text
这是“个人造价数据库管理平台”项目。请先阅读 README、PRODUCT.md、
相关 docs 和本目录的代码，再处理任务。

当前任务：<一句话目标>。
范围：<允许修改的模块>。
不要改：<用户正在修改或本轮无关的内容>。
完成定义：<测试、构建、页面行为或文档结果>。
请直接执行，并在过程中简短汇报发现和决定。
```

### 14.2 只做诊断，不改代码

```text
请诊断 <现象>，本轮不要修改文件。
先复现，再缩小范围，给出根因证据、受影响范围和修复选项。
不要根据报错文字直接猜结论。列出你实际运行的检查和结果。
```

### 14.3 要求修复

```text
请修复 <问题>。保留现有行为和用户未提交改动。
先添加能复现问题的测试，再做最小修复；运行相关测试和完整构建。
如果发现问题根因与我的描述不同，以证据说明后按真实根因处理。
```

### 14.4 要求代码审查

```text
请审查当前改动。优先找会导致错误数据、来源丢失、重复导入、
安全边界失效、恢复失败或用户流程中断的问题。
先列问题，按严重程度排序，并给出文件和行号；没有问题要明确说。
本轮不要修改代码。
```

### 14.5 继续上一次工作

```text
请先读取 git 状态、最近提交、相关文档和现有测试，确认当前基线。
上次目标是 <目标>，已知完成到 <状态>。不要假设聊天记忆是最新真源。
从未完成的验收项继续，完成后更新对应文档。
```

### 14.6 让 Codex 整理交接

```text
请把本轮决定沉淀到项目文件中：更新 README 当前状态，
把稳定约束写入架构或设计文档，把未决问题写入待办/决策记录。
同时输出下一位执行者的第一步、验证命令和已知风险。
不要只在聊天里总结。
```

## 15. 如何组织多个聊天，避免上下文失控

### 推荐的任务划分

- 一次聊天处理一个里程碑或一个明确问题。
- 需求、数据审计、架构、UI、纵向闭环和交付分别开任务。
- 同一任务中需要并行研究时，可以明确要求 Codex 使用子任务，但最终结论仍回写同一套项目文件。
- 新任务开始时，要求 Codex先读项目真源，不依赖“你应该记得上次”。

### 每次聊天结束前留下四类信息

1. **结果：** 实际增加或改变了什么。
2. **证据：** 哪些测试、构建、样本或截图证明它成立。
3. **风险：** 什么尚未验证，什么只是假设。
4. **下一步：** 下一轮最小可执行任务是什么。

### 建议的项目真源

| 文件 | 作用 | 什么时候更新 |
| --- | --- | --- |
| `README.md` | 当前状态、启动与验证入口 | 每个可运行里程碑 |
| `PRODUCT.md` | 用户、产品目的、体验原则 | 用户或产品定位变化时 |
| `docs/产品需求文档-*.md` | 范围、流程和验收 | 需求确认或变更时 |
| `docs/数据审计报告-*.md` | 样本事实、字段和模板差异 | 新模板或样本验证后 |
| `docs/技术架构调研与选型-*.md` | 技术决定和重新评估门槛 | 架构变化时 |
| `DESIGN.md` | 视觉与交互规则 | 设计系统变化时 |
| `docs/决策记录/` | 单项重大取舍及理由 | 发生难以逆转的决定时 |
| 测试与黄金样本 | 可执行验收依据 | 每次行为变化时 |

## 16. 如何判断 Codex 是否真的完成

不要只看“已完成”的文字。至少检查以下证据：

- 文件确实存在，引用路径没有失效。
- 测试被收集并通过；退出码为 0；不是“0 个测试”。
- 前端完成 TypeScript 检查和生产构建。
- 后端能在临时数据目录初始化并访问健康检查。
- 数据迁移在空库执行成功。
- 关键业务用真实脱敏样本跑通。
- 失败路径有明确结果，例如未知模板进入异常报告。
- 文档中的命令与仓库当前结构一致。
- Codex 明确报告未执行或失败的检查，没有把它们包装成成功。

可直接使用的验收追问：

```text
请不要再概述实现。现在只做交付核验：逐项运行验收命令，
记录命令、退出码和关键输出；检查文档中所有文件路径是否存在；
列出“通过 / 失败 / 未执行”。任何失败都不要写成已完成。
```

## 17. 常见失败方式与纠正方法

### 失败 1：第一句话就要求“把整个项目做完”

结果通常是大量未经验证的代码。纠正方法是把目标缩成一个真实纵向闭环，并给出样本和验收标准。

### 失败 2：没有真实 Excel，就先做通用解析器

结果是表头别名和关联逻辑靠猜。纠正方法是先做数据审计，用黄金样本驱动解析器和回归测试。

### 失败 3：只要求界面好看

结果可能缺少异常、证据、批量操作和失败状态。纠正方法是先给任务流、数据状态和专业边界，再谈视觉语言。

### 失败 4：把“代码已生成”当作“功能已完成”

纠正方法是要求实际运行测试、构建、迁移和端到端样本；对失败给出退出码和阻塞原因。

### 失败 5：所有决定只留在聊天里

新任务会重新讨论甚至得到相反答案。纠正方法是每个里程碑更新真源文件和决策记录。

### 失败 6：没有声明“本轮只诊断”或“允许修改”

任务边界容易模糊。纠正方法是在指令中明确授权范围、禁止改动和交付物。

### 失败 7：一次要求大规模重构和新功能

结果难以判断回归来自哪里。纠正方法是先建立测试，再分别做结构调整和行为变化。

## 19. 一页执行清单

### 开始前

- [ ] 明确一个可验收目标，而不是“做完整个平台”。
- [ ] 告诉 Codex 需要先读哪些文件和样本。
- [ ] 写清允许修改和禁止修改的范围。
- [ ] 给出交付物和验收命令。

### 执行中

- [ ] 要求 Codex 区分事实、假设、待验证和决定。
- [ ] 对关键技术取舍要求证据和重新评估门槛。
- [ ] 先做真实纵向闭环，再扩展横向功能。
- [ ] 涉及数据时坚持原件只读、来源追溯和异常不静默丢弃。

### 结束前

- [ ] 测试确实被收集并通过。
- [ ] 构建、迁移和关键样本流程实际运行。
- [ ] 文档和代码状态一致。
- [ ] 关键决定已经写入项目真源。
- [ ] 留下结果、证据、风险和下一步。

## 20. 最后的判断标准

与 Codex 协作的质量，不取决于一轮生成了多少文件，而取决于是否建立了一个不断缩小不确定性的过程：每轮只解决一个关键问题，用真实资料约束方案，用可执行检查验证结果，再把稳定结论写回项目。

对个人造价数据库这类专业数据系统，最好的推进顺序是：先把用户目标和数据事实弄清楚，再选择简单可控的架构；先证明一条导入、复核、发布、查询、追溯的闭环，再加入匹配、AI 和更丰富的界面。这样得到的不只是“Codex 写过的一套代码”，而是一套别人可以理解、验证、接手和继续演进的工程。
